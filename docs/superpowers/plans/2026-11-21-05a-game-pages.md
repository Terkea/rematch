# M5a Game Pages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The signed-in player sees their analysed games in the real app: an overview (accuracy over time, mistakes per game, results and accuracy by time control, analysed and waiting counts), a games explorer (filters, sorting, paging), and a single-game review (board, move navigation with keys, eval bar, eval graph, judgements, best-move arrows, clocks, the analysis reveal).

**Architecture:** `apps/web` reads the TS worker's existing tables (`games`, `moves`, `position_evals`, `import_runs`, `linked_accounts`) through a read-only server module, `apps/web/src/server/{games,stats,overview}`. Every query is scoped to the user's `account_links` and runs in a `READ ONLY` transaction. The pages are server components that call this module directly, so there are no new API routes. Client islands handle the board, the keys and the motion. Charts and review widgets are new `@ci/ui` components, built on visx, Motion and the M4 tokens. Statistics follow the honesty rules: each rate carries its n and an 80% interval, and below 10 games the page says "Need N more games" instead of showing a number.

**Tech Stack:** Next 16.4.6 App Router, React 19.3.1, Drizzle 0.45.4 on postgres 4.1.1, `@ci/ui` (Board, EvalBar, EvalGraph, KpiStat, Sparkline, Stat, AnnotationLayer, primitives, Motion tokens), `@ci/chess-core` (`parsePgn`, `fenKey`, `winningChances`), chess.js 1.4.0, @visx/visx 4.0.0, @tanstack/react-query 5.107.1, Vitest 5.1.0 with Testing Library and jsdom, and @playwright/test 1.65.1. **No new dependencies.**

## Global Constraints

- Read-only: no M5a code writes to `games`, `moves`, `position_evals`, `import_runs` or `linked_accounts`, and there is **no new migration**. The two exceptions are test helpers and the dev-only link script (Task 12), which writes only `account_links`.
- Scope: a user sees a game only when the game's `account_id` is one of the user's `account_links`, verified or not (ruling R1). Any other game id returns `notFound()`, never 403, so no id is confirmed to exist.
- Honesty (§12a, owner): no number is shown from zero evidence. No `NaN`, `Infinity` or `undefined` is ever rendered. Every rate or mean shows its n ("Based on 38 rapid games") and an 80% interval. Below `KPI_MIN_GAMES = 10` the page shows "Need N more games" (singular "Need 1 more game") instead of the value. Rates use Wilson intervals, and means use a seeded bootstrap with 2000 resamples. Games whose analysis isn't `done` count toward the status counts only, and every section says how many analysed games it is based on.
- ESM, TypeScript `strict` and `noUncheckedIndexedAccess`, with relative imports ending in `.js` in packages (apps/web keeps its existing style). Packages use the `@ci/*` scope.
- UI uses only `@ci/ui` tokens and components. No raw hex or arbitrary Tailwind values outside the M4 exemptions, and `pnpm design:check` reports `0 findings`. Icons come only from `@ci/ui/icons`.
- Ban list B1–B18 (DESIGN.md). Of note here: no stat-banner rows (B9; KPIs are list rows), no card grid (B4), no all-caps eyebrows or `A · B · C` meta strings (B5), no `→` on links or buttons (B5b), no spinners (B18; use `ProgressPlaceholder`), and no fade-up on every section (B11).
- Colour carries chess meaning: `pen` red is the player's own mistake, `pencil` is the opponent's mistake or an idea, and `good` is the better move. Red and green are never series colours. Every encoding is redundant (shape or pattern as well as colour).
- Copy: sentence case, British spelling ("analysing", "colour"), active verbs, the real minus sign U+2212 in evals, and "v" between player names. Actions keep their names. Errors say what happened and how to fix it.
- Quality floor: 360px with no page-level horizontal scroll, visible keyboard focus, WCAG AA, `prefers-reduced-motion` (marks appear in their final state, with no travel), and a keyboard-operable review.
- Motion: only transform, opacity and SVG `stroke-dashoffset`; motion is interruptible and never blocks input; tokens come from `@ci/ui/motion` (`dur`, `ease`, `spring`, `stagger`).
- The owner's games never become committed fixtures. Tests use the public fixture games in `@ci/ui/fixtures` (DrNykterstein) and synthetic rows, which are allowed in tests only (B15 covers UI).
- Dates are shown in UTC at day precision, "12 Nov 2026", in a `<time dateTime>` element (ruling R6).

## Rulings (the owner delegated all choices; each is recorded in the ADR named)

- **R1 (ADR 0046):** Data access covers every link the user holds, verified or pending, matching T22's `userAccountIds`. chess.com games are public, and an unverified link is labelled "Unverified" on the overview. If wrong, the cost is one `where verified_at is not null`.
- **R2 (ADR 0046):** No API routes. Server components call the read model, and the URL holds all list state.
- **R3 (ADR 0047):** `KPI_MIN_GAMES = 10`, `TREND_WINDOW = 20` games (a rolling mean with a band, shown once the window holds at least 10 games), `CONFIDENCE = 0.8`, and `BOOTSTRAP_RESAMPLES = 2000`. The seed is the FNV-1a hash of the sorted game ids, so server renders are deterministic. Score % is `(W + D/2) / n`, with a Wilson interval on that fraction.
- **R4 (ADR 0047):** Weekly trends cover the 12 ISO weeks ending in the week of the **latest analysed game**, not "now", so a player returning after a break still sees their last stretch, and the visual baselines stay deterministic.
- **R5 (ADR 0048):** The explorer uses offset paging (`PAGE_SIZE = 25`, a 1-based `page`, and a total count shown as "Showing 26–50 of 412 games"). A page past the end clamps to the last page, and invalid params fall back to their defaults.
- **R6 (ADR 0048):** Date filters are inclusive UTC days (`from` and `to` as `YYYY-MM-DD`). Dates are shown in UTC at day precision.
- **R7 (ADR 0049):** Engine scores come from `position_evals` (White's point of view), keyed by `fenKey` and the game's `analysis_protocol`. A missing row is filled from the stored win%, which inverts exactly, and the score is marked `source: "derived"`, shown with "≈". Classification uses only what is stored: `blunder`, `mistake` and `inaccuracy` from `moves.judgement`, plus `best` when `uci === bestUci`. There is no `!` or `!!`, because nothing stored supports brilliance.
- **R8 (ADR 0051):** On the review board, a judged move at the shown ply draws: a pen ring on its destination (mistake and blunder, player only), the glyph badge (pen for the player, pencil for the opponent), the pen arrow of the played move (blunder only), and the `good` arrow of `bestUci` when it differs from the move played. The "Show engine move" switch (off by default) adds a `pencil` arrow for the best move in the shown position.
- **R9 (ADR 0051):** Sounds are not wired in M5a. `GameReviewView` calls a single `onStep(kind: "step" | "play" | "jump", ply)` hook, which M4 T12b uses to play sounds (step and play only, never scrubbing).
- **R10 (ADR 0052):** The full analysis reveal runs on the first view of a game on this device (`localStorage` key `ci.review.seen`, at most 500 ids, oldest evicted, with every access in try/catch). Later views get the condensed version. Any key, pointer press or "Skip" jumps to the end state. "Replay analysis" re-runs the full version. Climax moments are the **player's** judged moves only, ranked by `deltaW` descending.
- **R11 (ADR 0050):** The accuracy chart plots the most recent 500 analysed games, and says so. Result is shown by dot shape: a filled ink dot for a win, a half-filled dot for a draw, and a hollow ring for a loss.

## Review Focus

1. **Someone opens a game id that isn't theirs**, whether another user's game, a game of an account they removed, or a malformed id. They get the not-found page, with nothing leaked and no 500. Tests: Task 3 `foreign game is not found`, `malformed id is not found`, and Task 1 `lists only the user's linked accounts`.
2. **A game whose analysis isn't done** (pending, analysing, failed or skipped) is opened, listed or averaged. The review replays the moves from the PGN with a placeholder where the evals would be. Lists show the status instead of an accuracy. Averages exclude the game and say "88 waiting for analysis". Tests: Task 3 `pending game replays without analysis`, Task 2 `accuracy ignores games not done`, and Task 9 `pending row shows status`.
3. **Tampered or stale URL params**, such as `?page=-3&tc=hyper&from=2026-13-40&sort=drop&account=<foreign uuid>`, or `?ply=9999` on the review. The page uses the defaults (or clamps the ply) and never errors or leaks. Tests: Task 1 `parseGameQuery falls back on bad input`, and Task 10 `ply param is clamped`.
4. **Tiny or uneven samples**, such as 0, 1 or 9 analysed games, a time class with one game, or a player who made no analysed move. The page shows no NaN, no interval below the minimum, "Need N more games", and counts that stay visible. Tests: Task 2 `estimate below minimum is insufficient`, `zero games gives no numbers`, and Task 8 `renders a one-game account without NaN`.
5. **Real games that stress the layout:** daily games with day-long clocks, PGNs without `%clk`, 300-ply games, long usernames and opening names, all at 360px. Clocks are hidden when absent and formatted in days when long. Long games scroll inside their own panels. Tests: Task 5 `formatClock` cases, Task 3 `game without clocks has hasClocks false`, and Task 13 `no horizontal scroll at 360px` on all three pages with a 300-ply seed.
